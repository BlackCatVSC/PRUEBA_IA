--------------------------------------------------------------------------------

2.1.1. README.md
- Propósito: Introducción al módulo de observabilidad.
- Contenido: Explica que se aprenderá a agregar logs y métricas básicas
  a agentes de IA para monitorear funcionamiento y desempeño.

2.1.2. presentacion.md
- 9 slides que cubren:
  * Slide 1: Objetivos (logging básico, métricas de rendimiento, debugging)
  * Slide 2: Importancia del monitoreo (problemas de "caja negra", beneficios)
  * Slide 3: Implementación práctica con logging y time
  * Slide 4: Tipos de métricas (performance, calidad, negocio)
  * Slide 5: Stack tecnológico (Python logging, Prometheus, Grafana,

  * Slide 9: Resumen ejecutivo

2.1.3. 1-observability_tools.py
- Clases principales:
  * RegistroMetrica: Dataclass para una interacción individual (timestamp,
    tiempo_respuesta_ms, tokens, éxito, modelo)
  * RecolectorMetricas: Recolecta y resume métricas (total, promedios, 
    tasa de errores)
  * AgenteObservable: Wrapper que registra cada interacción
- Funcionalidad:
  * Logging estructurado con timestamps (formato %Y-%m-%d %H:%M:%S)
  * Simulación de procesamiento con tiempos aleatorios (50-500ms)
  * Tasa de error simulada del 15%
  * Estimación de tokens basada en palabras
  * Reporte JSON con estadísticas agregadas
- Demo: 5 mensajes de prueba con reporte final

2.1.4. 2-observability-practice.ipynb
- Notebook práctico de 895 líneas con 6 secciones:
  * Sección 0: Configuración de entorno (GITHUB_TOKEN)
  * Sección 1: Sistema de Métricas (MetricaLlamada, RecolectorMetricas
    con estimación de costos, percentiles P50/P95)
  * Sección 2: Logging Estructurado (LoggerEstructurado con formato JSON,
    trace_id para correlación, 5 niveles de logging)
  * Sección 3: Agente Observable (integra métricas + logging con OpenAI,

- Dataclass: Modelado de datos (RegistroMetrica, Traza, Span, Solicitud, etc.)
- Wrapper: AgenteObservable envuelve la lógica del agente con métricas
- Observer/Collector: RecolectorMetricas acumula y resume datos
- Strategy: Diferentes modelos para diferentes complejidades
- Chain of Responsibility: Cadena de fallback entre modelos
- Circuit Breaker: Protección contra fallos en cascada
- Decorator: Funcionalidad añadida (logging, métricas) sin modificar núcleo

3.3. Conceptos Clave Transversales
- Observabilidad: Logging + métricas + trazas
- Trace ID: UUID único para correlación entre componentes
- Logging estructurado: Formato JSON para análisis automatizado
- Defensa en profundidad: Múltiples capas de seguridad
- Degradación elegante: Servicio reducido bajo carga
- Costo por token: Modelo de negocio basado en uso de LLMs

------------------------------------------------------------------------------
4.3.1. Cifrado de Datos
------------------------------------------------------------------------------

Cifrado en tránsito:
- Ya se obtiene por defecto usando conexiones HTTPS (TLS).
- En los notebooks del proyecto, las llamadas a la API de OpenAI ya usan
  HTTPS automáticamente. No requiere cambios.
- Verificación: asegurarse de no usar verify=False en requests.

Cifrado en reposo (para datos sensibles almacenados localmente):
- Usar la librería cryptography (pip install cryptography).
- Ejemplo de implementación para cifrar logs o configuraciones:

```python
from cryptography.fernet import Fernet

# Generar y guardar clave (una sola vez)
clave = Fernet.generate_key()
with open("clave.key", "wb") as f:
    f.write(clave)

# Cifrar datos antes de guardarlos
cipher = Fernet(clave)
datos = b"token_secreto_o_log_sensible"
cifrado = cipher.encrypt(datos)

# Descifrar al leer
descifrado = cipher.decrypt(cifrado)
```

- Dónde aplicaría en el proyecto:
  * Cifrar los logs antes de escribirlos a disco en IL3.2
  * Cifrar el archivo de configuración que almacena API keys
  * Cifrar datos de PII detectados antes de almacenarlos

------------------------------------------------------------------------------
4.3.2. Gestión Segura de API Keys y Secrets
------------------------------------------------------------------------------

Nunca se deben hardcodear claves en el código fuente.
El proyecto ya usa variables de entorno (GITHUB_TOKEN via python-dotenv),
lo cual es correcto. Mejora recomendada:

```python
# En lugar de depender solo de .env (que puede committearse por error),
# usar python-decouple que además soporta defaults y casting:

from decouple import config

GITHUB_TOKEN = config("GITHUB_TOKEN", default="")
OPENAI_API_KEY = config("OPENAI_API_KEY", default="")

if not GITHUB_TOKEN:
    raise EnvironmentError("GITHUB_TOKEN no configurado")
```

Otras buenas prácticas para secrets:
- Crear .env.example con valores ficticios y agregar .env a .gitignore
- Para producción, usar variables de entorno del sistema operativo
  en lugar de archivos .env
- No imprimir ni loguear claves (el proyecto ya evita hacerlo)

Impacto en el proyecto:
- Los notebooks ya cargan GITHUB_TOKEN desde .env (correcto)
- Solo falta agregar .env.example y verificar .gitignore
- Estos cambios son ~5 líneas de código y 1 archivo adicional
